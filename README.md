# وَمْضة

واجهة بسيطة للجوال والكمبيوتر، مع وضع فاتح وداكن. واجهة وأسئلة بالعربية، مع اتجاه من اليمين إلى اليسار.

اللعبة جولتان، كل جولة 10 أسئلة ومدة السؤال 20 ثانية. يختار المضيف قسمًا أو أكثر من البنك المفعّل ونظام النقاط قبل البدء. أول لاعب صحيح يكسب نقطة في وضع «أول لاعب»؛ وفي وضع «أول 3» أو «أول 4» يكسب الأول نقطتين والبقية نقطة. الترتيب حسب وصول الإجابة الصحيحة للسيرفر، والخطأ لا يحجز مركزًا. ينتهي السؤال باكتمال المراكز أو إجابة الجميع أو انتهاء الوقت. النقاط تراكمية، والمضيف يتحكم بالانتقال للسؤال التالي وبداية الجولة الثانية. تُختار 20 أسئلة مختلفة عشوائيًا من الأقسام المحددة، ويُرفض البدء إذا لم تكفِ الأسئلة.

تفاصيل التحديث والتجهيز المطلوب: [تقرير التصنيفات والصور والنقاط](docs/categories-update.md).

استعادة الجلسات والصلاحيات وحدود الاحتفاظ: [إعادة الاتصال وانتقال الهوست](docs/reconnection.md).

## التشغيل

افتح Terminal داخل مجلد المشروع، ثم شغّل:

```bash
npm install
npm start
```

افتح `http://localhost:3000` في المتصفح. لا تفتح `public/index.html` مباشرة؛ اللعب الجماعي يحتاج الخادم.

إذا كانت نسخة أخرى تعمل على المنفذ 3000، أوقفها أولًا باستخدام Ctrl+C. لو ظهر التصميم القديم، حدّث الصفحة باستخدام Ctrl+Shift+R.

بعد تعديل `server.js` أعد تشغيل الخادم؛ تحديث المتصفح وحده لا يحدّث الأسئلة أو قواعد اللعبة الموجودة في ذاكرة الخادم. للتحقق من النسخة افتح `http://localhost:3000/api/version`؛ يعرض الإصدار من `package.json` مع جولتين و10 أسئلة ومدة 20 ثانية.

## الواجهة

- تصميم بعمود واحد وأزرار مناسبة للمس، مع مقاسات مستقلة للكمبيوتر (من عرض 900 بكسل) والجوال. خلفية فاتحة بيضاء ودوائر ألوان ضبابية ثابتة، مع هيدر ثابت أثناء التمرير وقائمة جانبية بتأثير زجاجي. الوضع الداكن يحتفظ بخلفيته الرمادية مع تخفيف ألوان الخلفية.
- قائمة جانبية من اليمين تضم تغيير الاسم، نظام اللعب، الوضع الفاتح / الوضع الداكن، ووضع المطور. تدعم الإغلاق بالضغط خارجها أو Escape وتحترم تقليل الحركة. نافذة نظام اللعب مؤقتة حتى تحديد محتواها.
- تغيير الاسم ينعكس لدى لاعبي الغرفة دون فقد النقاط. تُرفض الأسماء الفارغة أو المكونة من أرقام فقط، بما فيها الأرقام العربية، في الواجهة والسيرفر باستخدام نفس دالة التحقق. يُمسح الإدخال غير الصالح ويظهر التوجيه داخل الحقل؛ العنوان والإطار والرسالة بالأحمر `#FF4D4D` في الفاتح وبالبرتقالي `#FF6D42` في الداكن. حقل الاسم العادي بخط سفلي محايد داخل بطاقة واحدة، وزر المتابعة مستقل أسفلها؛ التركيز على الحقل لا يستخدم البرتقالي.
- عنوان الرئيسية بوزن أخف، وكلمة «وَمْضة» فيه برتقالية في الوضع الداكن فقط. هيدر الوضع الداكن بدرجة أقرب للأسود مع الحفاظ على الشفافية والبلور.
- يبدأ المظهر باختيار الجهاز، ويحفظ اختيار المستخدم في المتصفح عند تغييره.
- الفوتر يعرض `Wamda © 2027` مع الإصدار المقروء من `package.json` عبر `/api/site`. لتحديث الإصدار استخدم `npm version <النسخة> --no-git-tag-version` لتحديث ملف الحزمة والقفل، ثم أعد تشغيل السيرفر. لا يحتاج رقم الإصدار إلى تعديل في HTML أو JavaScript.
- خط الواجهة «Tajawal / تجوال» مستضاف محليًا بأوزان حقيقية 400 و500 و700. لا يوجد وزن 600 رسمي في Tajawal. إعداد عائلة الخط مطابق لتعريف الخط العربي في ملف CSS المرجعي المرفق، والترخيص في `public/fonts/OFL.txt`.
- في نتائج الجولة الأولى يبدأ اللاعبون بأصفار بترتيب أبجدي عربي، ثم تزيد النقاط والصفوف ثابتة، وبعدها تتحرك مرة واحدة بسلاسة إلى مراكزها. عند تفعيل تقليل الحركة تظهر النتائج مباشرة.
- نسخ كود الغرفة وإظهار عدد اللاعبين، مع زر لمغادرة غرفة الانتظار.
- تظهر الإجابة الخاطئة بالأحمر والصحيحة بالأخضر، بما يشمل مربعات A وB وC وD، دون رسالة تصحيح نصية.
- عند تساوي النقاط تظهر مراكز متساوية، دون تغيير حساب النقاط.
- عند فقد الاتصال تُستعاد الجلسة والهوية والنقاط وحالة المباراة تلقائيًا. تظهر طبقة إعادة الاتصال بعد 800ms وتبقى حتى تطبيق حالة السيرفر. يحتفظ الهوست بصلاحيته 30 ثانية من اكتشاف الانقطاع، ثم تنتقل إلى أقدم لاعب متصل. تبقى الغرفة 24 ساعة دون أي متصل، وتفقد الجلسات عند restart/deploy للسيرفر.

## الملفات

- `public/index.html`: الشاشات.
- `public/style.css`: التنسيق المتجاوب وألوان الوضعين.
- `public/theme.js`: تبديل المظهر وحفظه، قبل تحميل التنسيق لتجنب ظهور المظهر الخطأ أولًا.
- `public/app.js`: أحداث الواجهة واتصال Socket.IO.
- `server.js`: إعداد HTTP وSocket.IO وربط مخزن الأسئلة والإدارة.
- `lib/multiplayer.js`: الجلسات والغرف والجولات والنقاط ومزامنة الحالة وانتقال الهوست.
- `public/settings.js`: القائمة وتغيير الاسم ولوحة المطور.
- `public/name-validation.js`: التحقق المشترك من أسماء اللاعبين في الواجهة والسيرفر.
- `lib/admin.js`: التحقق من كود المطور وصلاحيات الإدارة.
- `lib/question-store.js`: التحقق من بنوك الأسئلة وحفظها.
- `lib/default-questions.json`: الأسئلة المبدئية عند إنشاء مخزن جديد فقط؛ استخدم اللوحة لتعديل بنك محفوظ.

## الاختبارات

لتشغيل الاختبارات تحتاج Node.js 22 أو أحدث. تستخدم الاختبارات منفذًا مستقلًا تلقائيًا:

```bash
npm test
```

تشمل الاختبارات مباراة كاملة بعميلين حقيقيين عبر Socket.IO، انتهاء وقت السؤال، انتقال الاستضافة، وحفظ المظهر. وتشمل تنافس إجابتين صحيحتين معًا، رفض تكرار احتساب النقاط، حماية الإدارة، تعديل الاسم والتحقق منه، وحدود محاولات الدخول، وبقاء بنك الأسئلة بعد إعادة فتح المخزن. تشمل اختبارات الاستعادة أيضًا التحقق من token والاتصالين المتزامنين ومهلة الهوست ونقله المتكرر والغياب عبر الجولات ونهاية المباراة. اختبارات الواجهة تستخدم بديلًا مبسطًا لـDOM؛ ليست اختبارات عرض داخل متصفح.

تم التحقق في متصفح محلي بعروض 320 و390 و768 و900 و1440 بكسل من الواجهة في الوضعين الفاتح والداكن، واتجاه حقل الاسم وأخطائه، والفوتر، وفتح القائمة وإغلاقها بلوحة المفاتيح وتقليل الحركة. وفُحص إنشاء غرفة والانضمام وتغيير الاسم وقفل السؤال بعد أول إجابة صحيحة، والدخول إلى المطور وإدارة البنوك. اختبارات الواجهة تغطي أيضًا العد من الصفر والترتيب الأبجدي والتعادل وإلغاء الحركة عند بدء السؤال التالي.

مجلد `node_modules` غير مضمن في الأرشيف؛ ينشئه `npm install`. تُستخدم مكتبة `pg` للاتصال بـPostgreSQL عند إعداد `DATABASE_URL`.


## تشغيل وضع المطور على Render

1. ارفع **جميع** الملفات المعدلة والجديدة إلى GitHub، بما فيها `lib/` و`public/settings.js` وملفا `package.json` و`package-lock.json`. إعداد البناء: `npm ci`، والتشغيل: `npm start`.
2. في خدمة اللعبة على Render افتح **Environment**، وأضف `ADMIN_CODE` بقيمة سرية طويلة تختارها (يفضل 16 حرفًا أو أكثر). لا تضع الكود في ملفات `public` ولا ترفعه إلى GitHub.
3. أضف `DATABASE_URL` برابط PostgreSQL من Supabase في Environment على Render. نفّذ أولًا ملف `migrations/001_wamda_banks.sql` يدويًا من Supabase → SQL Editor → New query → Run، باستخدام دور `postgres`. عند التشغيل يُفحص الاتصال باستخدام `SELECT 1`، ثم يتحقق الخادم من وجود الجدول. إن كان موجودًا وفارغًا يحفظ البنك الافتراضي مرة واحدة؛ ولا يستبدل بنكًا محفوظًا. إذا لم تنفّذ SQL تبقى اللعبة بالأسئلة الافتراضية والإدارة للقراءة فقط.
4. البديل لقاعدة البيانات: اربط قرصًا دائمًا بخدمة Render المدفوعة، ثم عيّن `BANKS_FILE` لمسار داخل القرص مثل `/var/data/wamda/banks.json`. تعيين المسار وحده لا ينشئ قرصًا دائمًا.
5. احفظ الإعدادات وأعد النشر. افتح القائمة ← **وضع المطور**، وأدخل الكود.

بدون `ADMIN_CODE` يبقى دخول المطور معطلًا. وبدون قاعدة بيانات أو مسار تخزين دائم على Render تعمل اللعبة واللوحة للقراءة فقط وتُرفض تعديلات البنك؛ ملفات Render العادية مؤقتة. لم يُضف أي كود افتراضي للمطور.

- [ربط PostgreSQL على Render](https://render.com/docs/postgresql-creating-connecting)
- [الأقراص الدائمة على Render](https://render.com/docs/disks)

## استخدام لوحة المطور

- إنشاء بنوك متعددة وإعادة تسميتها وحذفها، وإضافة سؤال مع أربعة خيارات وتحديد الإجابة الصحيحة من A إلى D، ثم تعديل السؤال أو حذفه. لا يمكن حذف البنك المفعّل قبل تفعيل بنك آخر، ويمكن حذف الأسئلة مع منع بدء مباراة لا تملك 20 سؤالًا مختلفًا.
- تفعيل بنك للمباريات الجديدة بعد إضافة 20 سؤالًا مختلفًا على الأقل. تختار المباراة 20 سؤالًا عشوائيًا من التصنيفات التي حددها المضيف؛ يجب أن تكفي أسئلة هذه التصنيفات أيضًا.
- استيراد ملف JSON لإضافة أسئلة إلى البنك المحدد، أو تنزيل نسخة احتياطية منه. الاستيراد يقبل مصفوفة أسئلة أو كائنًا يحتوي `questions`، مثل النسخة المصدرة من اللوحة. الحد 500 سؤال و500 كيلوبايت للملف.
- عرض اللاعبين الذين أدخلوا أسماءهم وغرفهم، وعدد جميع الاتصالات والغرف. تتحدث القائمة كل 5 ثوانٍ ما دامت اللوحة مفتوحة. التبويبات المتعددة تُحسب اتصالات متعددة.
- تستمر المباراة الجارية بأسئلتها الأصلية عند تعديل البنك. التعديلات تطبّق عند بدء مباراة جديدة.
- الدخول محمي على الخادم، وتُقفل محاولات الدخول بعد 5 محاولات خاطئة لمدة 15 دقيقة لكل عنوان اتصال. تنتهي جلسة المطور بعد ساعة أو عند قطع الاتصال أو تسجيل الخروج. عند تشغيل الخدمة خلف وكيل قد تشترك الاتصالات في حد المحاولات.

صيغة السؤال في JSON (`correct` يبدأ من الصفر: A = 0، B = 1، C = 2، D = 3):

```json
{
  "question": "ما عاصمة المملكة العربية السعودية؟",
  "choices": ["الرياض", "جدة", "أبها", "الدمام"],
  "correct": 0,
  "categoryId": "science"
}
```

## تجربة الإدارة محليًا

انسخ `.env.example` إلى `.env`، وضع كودًا تختاره في `ADMIN_CODE`، ثم شغّل باستخدام Node.js 22 أو أحدث:

```bash
node --env-file=.env server.js
```

محليًا تُحفظ البنوك تلقائيًا في `data/banks.json` عند عدم إعداد قاعدة بيانات، والمجلد مستبعد من Git. لا يحفظ `npm start` متغيرات ملف `.env` تلقائيًا؛ استخدم الأمر أعلاه أو عيّن المتغيرات في بيئة التشغيل.

شغّل نسخة واحدة من خدمة اللعبة؛ الغرف والنقاط الحالية وجلسات المطور تبقى في الذاكرة وتنتهي عند إعادة تشغيل الخادم. التخزين الدائم يخص البنوك والتصنيفات وصورها، وليس الغرف الجارية.


## فحص اتصال Supabase عند بدء التشغيل

مكتبة `pg` مثبتة ضمن الاعتماديات، وتقرأ إعداد الاتصال من `process.env.DATABASE_URL` فقط. لا تُكتب بيانات الاتصال أو كلمات المرور في الكود أو السجلات. تعتمد إعدادات SSL على رابط الاتصال وإعدادات `pg` دون تعطيل التحقق من الشهادة في الكود.

بعد نشر التغييرات وإعادة تشغيل الخدمة، افحص **Render → Logs**:

- نجاح: `[PostgreSQL] Connection successful.`
- فشل: `[PostgreSQL] Connection failed. Check DATABASE_URL, network access and SSL settings.`

الفحص ينفذ `SELECT 1` فقط. بعده يحاول مخزن الأسئلة قراءة الجدول السابق إن وجد، دون تنفيذ `CREATE TABLE`. بعد التحقق من وجود الجدول، يحفظ البنك الافتراضي فقط إذا كان الجدول فارغًا. إذا فشل الاتصال أو كان الجدول غير موجود، تظل اللعبة تعمل بالأسئلة الافتراضية مع تعطيل تعديل البنك، منعًا لفقد التعديلات. وجود رابط الاتصال وحده لا يفعّل حفظ البنوك في قاعدة خالية من الجداول.

الاتصال الفعلي بقاعدة Supabase يحتاج متغير Render. الاختبارات تشمل محرك PostgreSQL محليًا عبر PGlite لتطبيق SQL والتحقق من الحفظ وإعادة فتح قاعدة البيانات والصلاحيات وتعارض التعديلات. هذا ليس اختبار اتصال بقاعدة Supabase المنشورة. تستخدم الاختبارات أيضًا اتصالًا محاكى وحالة فشل اتصال فعلي عبر `pg` للتأكد من بقاء اللعبة تعمل.

[دليل اتصال Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres) · [إعداد SSL في pg](https://node-postgres.com/features/ssl)


## تهيئة بنك الأسئلة — خطوة يدوية قبل النشر

الملف الكامل هو [migrations/001_wamda_banks.sql](migrations/001_wamda_banks.sql). يحفظ بنك الأسئلة في: `public.wamda_banks`، وفيه سجل واحد يحفظ البنوك والأسئلة والبنك المفعّل ورقم النسخة بصيغة JSONB.

1. افتح مشروع Supabase الصحيح ثم **SQL Editor → New query**.
2. اختر دور **postgres**، والصق **كل محتوى** ملف SQL، ثم اضغط **Run**.
3. تحقق من ظهور **Success**. لا نفترض أن الجدول أُنشئ قبل تنفيذ هذه الخطوة وتأكيدك ذلك. يمكن إعادة تنفيذ الملف دون مسح بيانات البنوك.
4. بعد تأكيد تنفيذ SQL ومراجعة التغييرات، يمكن نشر النسخة الجديدة لاحقًا. لم تنفذ مهمة تجهيز البنك أي push أو deploy.
5. بعد التشغيل، ظهور `[PostgreSQL] Question-bank storage ready.` في السجلات يعني أن الخادم حمّل البنك من الجدول. مجرد `Connection successful` لا يكفي.
6. افتح Developer Mode وأنشئ بنكًا وأضف له 20 سؤالًا مختلفًا أو أكثر، ثم فعّله. ابدأ مباراة جديدة لاختبار أسئلته. أعد فتح الصفحة واضغط **تحديث** لقراءة النسخة المحفوظة من قاعدة البيانات.

الحماية: تُفعّل RLS ويُمنع وصول أدوار `anon` و`authenticated` إلى الجدول. جميع عمليات الموقع تمر عبر Socket.IO في الخادم وتحتاج جلسة مطور صالحة. يجب أن يكون مستخدم `DATABASE_URL` مالك الجدول (`postgres` في إعداد Supabase المعتاد)، وليس مفتاح Supabase العام أو دور متصفح. لا يوجد سر داخل SQL.

لا يكتب الخادم SQL لإنشاء الجداول عند التشغيل. إذا كان الجدول غائبًا أو تعذرت قراءته، لا يُفترض أنه جاهز ولا تُحفظ تعديلات في ذاكرة مؤقتة كبديل. في PostgreSQL لا تظهر رسالة نجاح الحفظ إلا بعد نجاح الاستعلام، وتُرفض الكتابة فوق نسخة أحدث حتى يتم تحديث القائمة. بعد إنشاء الجدول يدويًا تحتاج إعادة تشغيل الخادم ليكتشفه إن كان قد بدأ سابقًا بوضع القراءة فقط.

إذا عندك أسئلة أضفتها في النسخة المحلية إلى `data/banks.json`، فهي لا تُرفع إلى GitHub تلقائيًا. صدّرها من لوحة المطور المحلية ثم استورد ملف JSON في البنك الذي تختاره على الموقع.

مكتبة `@electric-sql/pglite` ضمن `devDependencies` للاختبارات فقط. تشغيل الموقع يستخدم `pg` كالسابق؛ لا يتصل المتصفح مباشرة بـSupabase.
